# GCFeed 校招后端学习方案：从请求链路到故障与性能证据

制定日期：2026-10-30。

本方案直接从当前源码和本次验证结果出发，不采用已有学习路线。目标是独立理解、修改、验证并讲清项目；不包含安全专项。项目具体评估见同目录 `campus-backend-assessment-2026-10-30.md`。

## 1. 学习目标和时间假设

目标岗位按 Go 后端校招准备，基本工程知识也适用于其他后端岗位。默认已经接触过至少一门编程语言，每周投入约 15～20 小时；主体安排 8 周。周次是学习顺序，不是强制截止日期，未达到阶段验收就适当延长。

最终需要交付：

- 一个可重复启动和演示的项目。
- 三张自己能解释的链路图：Feed 读取、视频发布分发、互动状态变更。
- 两项由自己实现并验证的改进，至少一项包含故障恢复。
- 一份可重复的性能对比报告。
- 一套可以连续追问的项目讲稿与代码证据。

不要按文件数量衡量进度。一个模块的完成标准是：能说清输入、状态、事务、缓存、失败路径，并自己写出关键逻辑。

## 2. 先做能力自测

用一到两个学习时段完成：

1. 不看资料写一个 Go HTTP JSON 接口，定义请求/响应 struct。
2. 写一个实现接口的内存仓储，并注入 service。
3. 写出 `ORDER BY published_at DESC, id DESC` 对应的下一页条件。
4. 说明重复点赞为何不能每次都 `count+1`。
5. 画出“数据库提交成功、消息未发送时退出进程”的状态。

如果前两项难以完成，在正式计划前增加 1～2 周：练习 Go 的 struct、方法、接口、指针、slice/map、错误、包组织、context 和基本测试。用本项目缩小后的例子练习，暂时不研究 GMP 或复杂分布式方案。

如果五项都能独立完成，可缩短第一、二周，但不要跳过真实故障和集成测试阶段。

## 3. 为什么这样排序

```text
Go 与 HTTP 请求
    -> 单个数据库事务
    -> SQL 查询和游标
    -> 缓存读取与失效
    -> 消息、幂等和版本
    -> 关注流派生索引
    -> 推荐行为闭环
    -> 实验、复盘与面试表达
```

先掌握同步、确定的基线，再理解缓存和异步带来的新状态。三个重点模块投入不平均：Feed 最先学，互动一致性投入最多，关注流作为系统设计扩展。账号、消息、播放模块用于补齐理解，不需要逐个做成复杂系统。

## 6. 第 3 周：深入 Feed 和 Redis 缓存

**目标：掌握第一条完整面试主线，建立测量基线。**

阅读入口：

- `internal/application/feed/service.go`：TimelineStrategy、loadFeedPage、assembleFeedItems
- `internal/infra/cache/feed_cache.go`：GetPage/GetCards/GetStats

学习内容：cache-aside、批量读取、TTL、缓存更新与失效、进程内请求合并、热点 key、连接池，以及“数据库是来源、缓存是派生结果”的含义。

动手任务：

1. 写出一个 timeline 请求经历的所有 SQL 和 Redis 操作，分别列匿名与登录情况。
2. 制作 key 表：key 格式、value 结构、来源、TTL、写入方、失效触发、故障行为。
3. 分别测无缓存、冷缓存、热缓存，记录 SQL 次数和响应延迟。
4. 删除或更新一条已缓存视频，观察旧卡片仍可见的条件，选择并实现失效方案。
5. 对被过滤的无效视频定义有限补页行为，避免无限回源。
6. 给同一个冷页并发请求，观察 singleflight 是否减少页回源；再用两个 API 实例说明它的进程边界。

建议第一项独立改进：**视频删除后的 Feed 缓存可见性与失效**。范围清楚，能串联业务、缓存和测试，避免一开始就重构全部缓存。

产物：Feed 时序图、缓存 key 表、第一项改进与回归测试、初始性能表。

验收问题：

- 为什么卡片与统计分开缓存？
- 为什么 page key 不包含 viewer_id 仍可能合理？哪些数据不能共享？
- singleflight 保护的是哪一步，保护不到哪些步骤？
- Redis 断开时各个 Feed 场景真的会发生什么？
- 空结果、删除条目、过期游标分别怎么处理？

## 7. 第 4 周：互动一致性，先复现再选择实现

**目标：掌握第二条核心主线，能区分各种失败。**

阅读入口：

- `internal/application/interaction/service.go`：setActionAsync/setActionSync
- `internal/infra/cache/feed_cache.go`：SetActionState 和 actionStat 系列函数
- `internal/application/interaction/worker.go`
- `internal/infra/persistence/interaction/gorm.go`

学习内容：读后写冲突、WATCH/事务、重试上限、最终一致性、读到自己的写、事件版本、状态恢复、计数基线与增量。

必须先复现以下场景：

| 实验 | 观察内容 |
| --- | --- |
| 数据库已点赞，Redis 行为 key 删除后取消 | delta 是否为 0，是否发消息，数据库是否改变 |
| 数据库已点赞，Redis 清理后重复点赞 | 基数是否被重复叠加 |
| 暂停 worker，点赞后刷新 Feed | 返回计数、liked 状态、数据库三者是否一致 |
| 点赞/取消事件逆序应用 | 最后状态是否符合接受操作的版本顺序 |
| 仅删除部分统计 shard | 缓存计数是否偏离真实有效行为数 |
| 同一行为并发修改 | 是否出现 WATCH 冲突，失败是否有界重试 |

实现选择：默认选择容易解释和验证的 **MySQL 事务状态基线 + 后续异步派生更新**。如果决定保留 Redis 优先写，先写清可靠记录事件、状态恢复、版本分配和部分失败协议，并接受额外投入。

不能为了性能保留一个自己无法说明恢复行为的方案。也不要误以为 outbox 可以自动跨越 Redis 和 MySQL 的事务边界。

产物：异常时序图、失败用例、选型说明、行为状态与计数的修复或简化。

验收问题：

- 重复消息为什么和乱序消息是两件事？
- 同一个用户先赞后取消，如何判断哪个更新较新？
- 接口返回成功到底保证了什么？
- 用时间戳当版本有什么前提和局限？
- 基数和增量怎样划定同一个统计周期？

## 8. 第 5 周：可靠消息与发布分发

**目标：完成一项能演示故障恢复的改进。**

阅读入口：

- `internal/application/video/service.go`
- `internal/infra/mq/rabbitmq.go`
- `cmd/worker/main.go`
- `internal/application/video/fanout_worker.go`
- `internal/application/embedding/worker.go`

学习内容：交换机、路由、队列、持久消息、publisher confirm、consumer ACK、至少一次投递、事务 outbox、消费者去重、退避、死信、重连和在途任务。

建议先对视频发布实现，范围比一次改造全部事件更可控：

1. 业务事务内写入视频和 outbox。
2. relay 扫描待发送事件，等待发布确认，再更新发送状态。
3. 设计多个 relay 的任务领取、租约失效或锁竞争处理。
4. 消费成功后 ACK，重复事件不会重复制造业务影响。
5. 加有限重试与失败隔离，记录错误和下一次重试时间。
6. 将事件产生时间带到观测中，测量发布到关注流可见的延迟。

必须演示：

- 数据库提交之后、消息发布之前退出，恢复后能补发。
- 消费业务提交之后、ACK 之前退出，重投不会破坏结果。
- 一条永久失败消息不会无限快速重试。
- broker 恢复后消费者能恢复工作，或明确需要重启并有可观测告警。

产物：第二项独立改进、故障注入脚本/步骤、恢复日志、正确性断言。

验收问题：

- 持久化消息、发布确认、消费确认分别解决什么？
- 为什么 outbox 仍可能重复发送？
- 幂等检查和业务写入之间还有没有竞态窗口？
- 怎么处理数据库已经成功而确认丢失？
- 一个消费者停了，进程仍活着时如何发现？

## 11. 第 8 周：压测、复盘和面试表达

**目标：把项目能力变成可验证的证据。**

### 压测设计

数据规模先从机器能承受的量级开始，例如 1 万视频作为起点，再按资源扩大；这是实验建议，不是当前项目已有规模。

| 场景 | 固定条件 | 要回答的问题 |
| --- | --- | --- |
| 时间线读 | 相同数据、limit、匿名/登录分别测 | 缓存和批量查询减少了多少数据库请求 |
| 冷启动读 | 同样空缓存、相同并发 | singleflight 是否减少页回源 |
| 深翻页 | 相同排序与目标位置 | cursor 与 offset 的扫描成本差异 |
| 普通互动/热点互动 | 相同用户数，均匀分布与集中视频分别测 | 锁竞争和计数操作瓶颈在哪里 |
| 发布 fanout | 不同粉丝数量、批次与消费者数 | 从发布到可见要多久 |
| worker 积压 | 暂停后恢复 | 收敛时间、重复处理和最终数据正确性 |

记录硬件、OS、Go/数据库/Redis/MQ 版本、数据规模、并发或到达率、预热时间、持续时间和提交版本。对同一场景至少重复几轮，保留原始输出，不只保留平均值。

指标：吞吐、P50/P95/P99、错误率、CPU/内存、数据库连接与锁等待、SQL 次数、缓存命中率、队列深度、消息延迟、恢复时间、数据差异数。

不要提前承诺“必须提升 50%”或固定 QPS。学习验收要求是实验方法有效、瓶颈解释成立、结果能复现。

### 最终产物

1. 一份性能前后对比，包含一项收益不明显或有代价的结果。
2. 两个故障案例：复现步骤、原因、方案、取舍、回归结果。
3. 三张能从空白画出来的链路图。
4. 一段 1 分钟项目介绍、一段 5 分钟讲解、一段 15 分钟深入讲解。
5. 三条只使用已完成事实的简历描述。

面试表达固定结构：

> 业务场景 -> 实际瓶颈/错误 -> 备选方案 -> 选择原因 -> 实现关键点 -> 验证结果 -> 剩余限制。

## 12. 每天怎样安排

一个约 2.5 小时的学习时段可分为：

| 时间 | 内容 | 必须留下的证据 |
| --- | --- | --- |
| 30 分钟 | 只读今天链路涉及的文件 | 输入、输出、依赖和状态笔记 |
| 60 分钟 | 自己实现、复现或修改 | 小范围 diff 或可运行实验 |
| 30 分钟 | 测试与观察 | 请求/SQL/日志/指标结果 |
| 30 分钟 | 基础题或算法练习 | 独立作答与错因 |

每周再安排一次 20 分钟脱离代码讲解。不能解释的地方回到实验，不靠背诵注释补过去。

## 13. 与项目并行的基础知识

项目不能替代校招的基础能力准备，但基础知识应尽量与当前链路连接。

| 主题 | 优先学习 | 在本项目中的连接点 |
| --- | --- | --- |
| Go | interface、slice/map、错误、context、goroutine、channel、mutex、race detector | 依赖注入、worker、并发请求、测试替身 |
| MySQL | B+Tree、联合索引、事务、隔离级别、MVCC、锁与死锁 | 游标分页、计数、互相关注 |
| Redis | String/Hash/ZSET、过期、淘汰、持久化基本概念、pipeline、WATCH | 页缓存、互动状态、inbox/outbox、热榜 |
| MQ | 发布确认、消费确认、重复、顺序、重试和积压 | 发布与互动 worker |
| 网络 | HTTP、连接复用、TCP 基本过程、超时、Range 请求 | API、依赖连接、视频播放 |
| OS | 进程/线程、调度、锁、文件 IO、内存基本概念 | Go 服务、ffmpeg 子进程、文件上传 |
| 算法 | 数组、哈希、链表、二分、堆、树、基础图搜索 | 面试编码；多路 Feed 归并可联系堆 |

从第 3 周起，再按需要深入 GMP、GC、逃逸分析与 pprof。不要在基础请求链路还讲不清时，把大部分时间投入运行时细节。

## 14. 资料使用方式

优先查官方文档的对应章节：Go Tour/Effective Go 与 `context`、`testing`、`net/http` 包文档；MySQL 8.4 的索引、EXPLAIN ANALYZE 和 InnoDB 锁；Redis 的数据类型、事务和过期；RabbitMQ 的 acknowledgements/confirms、消费者 prefetch 和可靠性。

这些是后续学习检索入口。本次外部检索未取得可引用正文，报告中的项目判断依据是本地源码和本地命令结果。学习具体 API 时，以实际使用版本的文档为准。

每次带着一个实验问题去查，例如“WATCH 冲突返回什么，谁重试”，不要从头背完整中间件手册。

## 15. 时间紧时的压缩方案

如果只有 4 周，保留主线，缩减范围：

1. 第 1 周：构建演示、完整请求、事务与游标；补 Go/SQL 基础。
2. 第 2 周：Feed 缓存链路和一项缓存正确性改进；留下性能基线。
3. 第 3 周：互动状态恢复与视频发布可靠性，至少完成一个真实故障恢复实验。
4. 第 4 周：关注流边界、压测、简历与模拟追问。

推荐模块先做到能准确解释实现和缺口，不强行上画像 worker、向量数据库或复杂算法。没有足够时间实现的设计，应标为后续方案。
