# GCFeed 全项目优化审查（2026-11-03）

本报告基于当前工作区，包含审查开始时已存在的未提交修改。仅新增审查文档，不修改业务实现。结论来自静态代码审查和本地测试，不代表已完成生产压测或真实中间件故障注入。

项目已经具备分层单体、Feed 策略、游标分页、批量卡片查询、缓存抖动、singleflight、推拉混合关注流、互动异步落库及基础监控。当前应优先完善跨存储的一致性和故障恢复，再优化热路径；拆分微服务暂不作为优先事项。

优先级：P0 为对外部署前应修复的问题；P1 为正确性与可靠性问题；P2 为性能和维护性优化。性能收益均需用实际数据验证。

## P0：访问边界与上传内容

### 1. 部分内部接口未鉴权

- 位置：`apps/api/internal/interfaces/http/router/router.go:187` 的 internal 路由注册；`interfaces/http/recommendation/handler.go`。
- 已确认：推荐候选、曝光决策、曝光写入三个接口未挂 InternalTokenAuth；用户 ID 来自请求体。消息、播放内部接口则有内部 token 校验。
- 影响：能访问 API 端口的调用者可以指定其他用户查询推荐或写入曝光记录。Compose 映射了 API 的 8080 端口；Web Nginx 没有代理 `/internal` 并不等于 API 本身受保护。
- 建议：在 internal 路由组统一校验服务身份，再设置部署网络访问限制；生产配置拒绝使用示例凭据。
- 验收：匿名调用所有内部接口均被拒绝；合法服务凭据调用正常；不能伪造其他主体写入曝光。

### 2. 通用文件上传与网站同源访问组合存在脚本执行风险

- 位置：`interfaces/http/upload/handler.go:193,215,263`；`interfaces/http/router/router.go` 的 Static 路由；`apps/web/nginx.conf`；`apps/web/src/App.jsx:47`。
- 已确认：kind 缺省或为 file 时允许通用文件，保留扩展名并跳过 MIME 检查；上传结果通过 `/uploads/` 提供访问，前端将 token 放在 localStorage。
- 风险推断：允许上传 HTML 等主动内容时，其他用户打开相应同源 URL 可能执行上传者脚本，进而访问该源的本地存储。此项未进行浏览器利用验证。
- 建议：产品若只需视频、封面、头像，关闭通用 file 类型；确需附件时使用独立资源域、下载响应和严格类型策略。先处理主动内容入口，再评估 token 存储方式。
- 验收：危险主动内容无法作为网站同源页面执行；正常视频 Range 请求和封面访问仍然有效。

## P1：正确性、数据一致性与可恢复性

### 3. Redis 行为状态缺失时错误地认为用户没有点赞

- 位置：`infra/cache/feed_cache.go:437`；`application/interaction/service.go` 的 setActionAsync。
- 已确认：只从数据库读取视频总计数，未读取该用户原始 action；Redis 无 status 时，点赞产生 +1，取消产生 0。
- 触发：用户在数据库中已经点赞，Redis action key 因过期、重启或淘汰丢失；此时取消点赞不会产生事件，数据库仍保持已点赞。再次点赞则可能在缓存重复计数。
- 建议：缓存缺失时恢复用户行为状态和对应版本；把状态变更及待发送事件纳入可靠写入协议，避免“缓存已变、事件未产生”。
- 验收：已有点赞 → 清除该 action key → 取消点赞，最终数据库、缓存及 Feed 状态一致。

### 4. 分片计数的 TTL 与基数生命周期不一致

- 位置：`infra/cache/feed_cache.go:493,497,542,604`。
- 已确认：每次互动刷新公共 base 的 TTL，只刷新本次命中的 shard TTL；base 字段用 HSetNX 初始化。
- 触发：一个 shard 长期不活跃而过期，其他 shard 持续活跃，使 base 保留旧值；已过期 shard 的历史增量不再参与求和，显示计数下降。
- 建议：设计带版本或 epoch 的基数与增量归并协议，明确何时把已持久化增量折叠到新基数；不能只延长 TTL。评论更新也需避免被旧 base 中的 comment_count 覆盖。
- 验收：模拟 shard 独立过期、base 重建、评论与点赞并发，结果与数据库基准对齐。

### 5. 视频发布与观看事件没有可靠投递闭环

- 位置：`application/video/service.go:91`；`application/exposure/service.go`；`infra/mq/rabbitmq.go:89`。
- 已确认：数据库成功后直接发布，发布错误被忽略；没有发现事务 outbox、发布确认或后台补发流程。视频幂等重试命中已有记录后直接返回，也不会补投。
- 影响：发布成功但未进入关注流分发、未计算向量；观看事件可能缺失。单独增加 publisher confirm 仍不能消除数据库提交与消息发送之间的进程崩溃窗口。
- 建议：视频和观看事件采用同事务 outbox + 可重试 relay；互动链路明确数据库优先或 Redis 原子状态/事件日志方案；所有消费者按事件 ID 与业务版本保证幂等。
- 验收：数据库提交后终止进程、MQ 断开、重复投递，最终仍能完成处理且不重复产生业务效果。

### 6. 互动事件缺少版本保护

- 位置：`application/interaction/worker.go`；`application/interaction/service.go` 的 ActionChangedEvent；`infra/persistence/interaction/gorm.go:99`。
- 已确认：worker 按事件中的目标状态直接 SetAction；EventID、OccurredAt 未用于限制陈旧事件覆盖；存储只保留最近一次请求幂等键。
- 影响：失败重投、并发请求或将来增加消费者后，旧点赞事件可能覆盖较新的取消事件。
- 建议：针对 user/video/action 分配单调版本，数据库仅接受新版本；消费去重与版本检查置于同一事务。
- 验收：按新、旧、重复顺序投递事件，最终状态始终对应最新版本。

### 7. MQ 消费的失败处理和连接恢复不足

- 位置：`infra/mq/rabbitmq.go:161,205,241`；`cmd/worker/main.go`。
- 已确认：业务失败立即 Nack(requeue=true)；拓扑未配置死信重试策略；没有设置 Qos；消费 channel 关闭后 goroutine 退出，但主进程仍等待退出信号，没有重新建立消费者。
- 建议：设置 prefetch 和并发上限；区分永久错误与临时错误，有限次数退避后进入死信；监测连接与消费者状态，重连后重建拓扑/订阅；退出时等待在途任务。
- 验收：MQ 重启后自动恢复；坏消息不会无休止快速重投；消费者断开会影响 readiness 或触发明确告警。

### 8. 观看行为队列存在发布端，但 worker 未接入消费者

- 位置：`infra/mq/rabbitmq.go` 的 ConsumeViewEventRecorded；`cmd/worker/main.go` 的 startWorkers。
- 已确认：启动入口只注册互动、视频分发、视频向量三个 worker，未调用观看行为消费方法；配置启用 MQ 时观看服务会向相应队列发布。
- 影响：在当前仓库的部署范围内，该队列没有对应消费处理链路，会积压；用户画像仍由推荐请求现场读取历史事件计算。
- 建议：实现幂等的用户画像消费者并注册，或在功能尚未落地时关闭该事件发布；对队列深度和最老消息年龄告警。

### 9. 取关后 inbox 旧内容未被过滤

- 位置：`application/relation/service.go` 的 setFollow；`infra/cache/feed_cache.go:282,340`。
- 已确认：取关只修改关系；读取索引时仅对 outbox 来源检查作者集合，inbox 条目没有检查当前关系。
- 影响：缓存命中时用户取关后仍看到该作者。
- 建议：读取时批量检查当前关注关系，同时异步移除相应 inbox 内容；避免为每条视频逐个查库。
- 验收：关注 → 缓存收件箱 → 取关 → 读取关注流，不出现已取关作者。

### 10. 关注索引“存在”不等于“完整”

- 位置：`infra/cache/feed_cache.go:313`；`application/feed/service.go:474`；`application/video/fanout_worker.go`。
- 已确认：只要任一 ZSET 非空就返回 ok=true，应用层直接采用结果。inbox/outbox 分别截断到有限长度，部分 key 过期或缺失不会触发完整回源。
- 影响：部分缓存丢失、翻到截断边界、作者跨大 V 阈值时，可能漏内容或过早返回无下一页。
- 建议：记录索引覆盖范围、生成版本和历史边界；覆盖不足时与数据库结果合并；大 V 阈值迁移需要回填策略。
- 验收：删除单个作者 outbox、越过截断边界、作者跨阈值，均保持分页完整性。

### 11. 关注流 score 与游标排序不完全一致

- 位置：`infra/cache/feed_cache.go:299,720,762`。
- 已确认：score 用秒级时间和 videoID % 1000000 组合；结果排序与游标使用完整时间和完整 ID。
- 影响：同一秒内 ID 余数跨界、score 冲突或存在亚秒时间时，Redis 范围过滤可能与最终排序不一致，造成漏项。
- 建议：采用能严格表达实际排序元组的编码方案，或扩大候选范围后用完整元组过滤；明确并测试相同时间的顺序规则。
- 验收：覆盖同秒 ID 999999/1000000、相同余数 ID、亚秒时间等边界。

### 12. 删除视频没有缓存失效闭环

- 位置：`application/video/service.go:151`；`application/feed/service.go:24,593`。
- 已确认：Delete 更新数据库状态，没有发布删除事件或失效缓存；组装 Feed 时命中 card 就使用，不重新检查发布状态；card TTL 为 15 分钟。
- 影响：仍含视频 ID 的 inbox、outbox、热榜或页缓存可继续组装已删除视频。实际可见窗口取决于这些索引和缓存的存活情况。
- 建议：删除事件可靠投递，失效 card 与相关索引，并用短期 tombstone 或内容状态过滤阻止重新组装。
- 验收：先预热各 Feed 场景再删除，所有场景在约定时限内不可见。

### 13. 推荐分页使用实时变化的分数

- 位置：`application/recommendation/service.go:99,246,374`；`infra/persistence/recommendation/gorm.go:38`。
- 已确认：每页重新召回有限候选并计算热度、新鲜度与用户兴趣分数，再按上一页分数过滤；request ID 没有关联固定候选快照。
- 影响：跨分钟、互动变化或用户产生新观看事件后，分页排序基础变化，存在重复或漏项风险；有限候选池耗尽也不代表所有视频耗尽。
- 建议：为一次推荐会话保存短期候选 ID 快照或固定排序版本，游标携带快照 ID 和位置；过期后显式重启会话。
- 验收：第一页后改变热度、画像和时间，后续页仍遵循已定义的稳定会话语义。

### 14. 前端翻页响应缺少场景隔离

- 位置：`apps/web/src/App.jsx:482`、`:2637`。
- 已确认：loadMoreFeed 回调直接追加数据，没有核对当前 request ID 或 scene；apiRequest 未接收 AbortSignal。首次 loadFeed 的 live 标志不能保护翻页请求。
- 触发：场景 A 请求下一页未完成时切换到 B，A 的响应随后追加进 B。
- 建议：请求绑定 scene、用户、会话版本；响应落地前核对版本；切换与卸载时取消旧请求；旧请求的 finally 也不能清除新请求的加载状态。
- 验收：人为延迟 A 翻页，切换 B 后再完成 A 请求，B 列表与游标不受影响。

## P2：性能、工程与运行优化

### 15. 热路径减少串行往返，但先保留正确性约束

- Feed 卡片、计数、用户互动状态在 `application/feed/service.go:593` 串行加载；可把独立读取做有界并发或合并 pipeline。
- 计数 JSON 缺失时，`infra/cache/feed_cache.go:152` 逐视频回退读取；单视频内部已对分片使用 pipeline，仍可按整页聚合，减少跨视频串行轮次。
- 异步互动每次仍先查询 MySQL 视频统计，新增点赞通知也含同步资料读取与消息写入。应统计实际 SQL 次数后决定缓存/异步化边界。
- `infra/persistence/interaction/gorm.go:404` 锁定视频行，同视频的不同用户互动会争用该锁；还会锁统计行。优化时必须保留删除与互动之间的一致性，不能直接删锁。
- 验收：分别记录缓存命中/未命中请求的 Redis 往返、SQL 数量、锁等待和 P95/P99。

### 16. 推荐召回与曝光写入成本

- `infra/persistence/recommendation/gorm.go` 按 join 后计算出的 hot_score 排序；是否成为瓶颈需用真实数据执行计划确认。
- 每次推荐读取并解析候选 JSON 向量，再从最多 200 条历史事件重建用户兴趣。
- SaveExposures 在事务内逐视频校验、插入、upsert、再读取，批量请求仍有多次数据库往返。
- 建议：预计算或缓存候选集合和用户向量；先做批量读取/写入，再根据规模评估更复杂召回设施。已有 timeline 复合索引应保留，不应笼统重复添加。

### 17. 预加载应该针对实际下一条视频

- `apps/web/src/App.jsx:629` 在不同 Feed 场景都调用预加载接口。
- `infra/persistence/playback/gorm.go:40` 按时间线返回当前视频之后的资源，没有推荐/热榜会话顺序。
- 建议：优先预热当前列表中的实际下一条；结合网络类型、节流和并发预算。限制已浏览 items、曝光集合、预热集合长期增长。
- 前端目前只渲染当前/切换中的视频，不应把它误判为一次渲染整个视频列表。
- 验收：测量预加载命中率、额外下载字节、首帧时延和低速网络下的卡顿。

### 18. 上传与媒体服务隔离资源消耗

- `interfaces/http/upload/handler.go` 已有限额、元数据检查、ffprobe/ffmpeg 超时及 faststart，应保留。
- 当前处理在 HTTP 请求内同步执行，未发现进程并发上限；大文件流量也经 Nginx 转发到 API。
- 建议：先加入上传配额、并发信号量与临时文件/未引用文件清理；规模增长时采用对象存储直传和异步 processing/ready/failed 状态。发布必须校验资源 ready。
- 验收：并发上传时 CPU、磁盘和业务 API 延迟保持在预算内；中断与失败文件可清理。

### 19. 监控标签、健康检查与生命周期

- `infra/metrics/metrics.go:153` 在未匹配路由时用原始 URL path 当指标标签，任意不同 404 路径可产生大量序列。统一使用固定 unmatched 标签；Feed 的未知 scene 也应归一化。
- `/health` 固定返回成功；消费者退出后 worker 进程也可能仍存活。区分 liveness 与 readiness，依据关键依赖和实际消费者状态判定。
- `infra/httpgin/gin.go` 直接 g.Run，未配置显式 server 超时和优雅关闭；API 装配创建的数据库、Redis、MQ 连接缺少统一释放入口。
- 建议：构造统一应用生命周期，设置请求/依赖超时、停机等待；记录 request ID 和内部原始错误；补队列积压、消费延迟、DB pool 等指标。

### 20. 数据库迁移、配置与维护成本

- API 与 worker 启动都会 AutoMigrate；timeline 索引还使用先查询再创建。多个实例同时启动时需避免迁移竞争。
- 数据库连接池固定为 50/10；未配置连接最大寿命、连接/查询超时预算。调优依据应为实例总连接数和等待时间。
- 建议：生产迁移独立执行并版本化，配置外部注入；示例口令与开发端口映射限定于本地环境；镜像使用可追溯版本。
- `App.jsx` 超过 2800 行，集合了页面、网络、会话、手势和 QoS；优先拆为业务页面、useFeed/usePlayback、API client 和 DTO 模块，再决定是否引入更多依赖。
- 后端 router 同时承担依赖装配和适配器实现；可移到 bootstrap。Cache 接口依赖 Application 类型也可以逐步整理到合适的业务端口位置。

## 测试与实施顺序

现有 API 测试使用内存仓储，Redis 计数测试也使用 fake；这类测试能验证业务编排，但不能证明真实 SQL 锁、Redis WATCH/TTL 或 MQ 断线恢复正确。不能根据 application 包显示 no test files 就断言业务没有测试，因为跨层测试集中在 `apps/api/test`。

`tests/k6/load_test.js` 主要反复请求首屏，推荐使用同一登录账户；业务成功检查只要求 items 是数组，空结果也计为成功。建议增加多用户、多页、冷热缓存、读写混合和依赖故障场景，同时测重复/漏项率、事件积压、异步收敛时间、P95/P99。当前审查没有取得可用于声称 QPS 提升的基准数据。

建议按以下批次实施，每批都附对应回归测试：

1. 对外访问边界：内部鉴权、上传主动内容、生产示例凭据。
2. 业务正确性：互动状态恢复/计数归并、关注过滤/索引覆盖、删除失效、前端竞态。
3. 异步可靠性：outbox、版本幂等、观看消费者、重试死信、断线恢复与 readiness。
4. 热路径验证：SQL 执行计划、缓存往返、热点锁、推荐向量缓存、实际下一条预加载。
5. 工程收尾：迁移、生命周期、可观测性、前端拆分与持续集成。

本地验证：`go test ./...` 已通过。前端按 package-lock 安装依赖后，`npm run build` 已通过；JS 产物为 195.06 kB（gzip 61.12 kB），CSS 为 32.62 kB（gzip 6.50 kB）。首次构建缺少 Vite、首次沙箱内安装出现 npm 异常，随后完成安装并成功构建。未启动真实中间件执行集成压测，未执行浏览器安全利用验证。
